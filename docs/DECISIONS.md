# SQLite migration decisions

1. The owner requested a database with no subscription and asked us to choose and implement it. SQLite is suitable for a small single-business operation: public-domain, embedded, transactional and portable as one main database file with WAL sidecars while running. No provider account/API credential is required.
2. The app now uses a self-hosted Node.js 22.16+ or 24 server and its built-in node:sqlite/http/crypto modules. There are no runtime npm dependencies and no frontend build step. Node itself must be installed; npm/Playwright/Prettier are only development tools.
3. This replaces GitHub Pages + Supabase, including Auth, Realtime and Edge Functions. GitHub still stores source and runs CI, but cannot host a writable SQLite server through Pages. A test workflow runs CI; the Pages workflow now publishes only a setup notice so old public links do not keep showing the superseded Supabase UI. Public hosting/HTTPS availability is separate from a free database; no free always-on hosting claim is made. LAN access works while the server computer is running.
4. Earlier Supabase/prototype source remains in Git history. No hosted project/config/data was supplied, so nothing was exported/imported from Supabase. An older prototype data/laundry.sqlite is preserved and unused. The new file is data/platform.sqlite. Existing real hosted customers, if any were added outside this task, need a separate migration before switching live operations.
5. Owner and rider pages keep their UI. shared/api.js adapts the existing query-oriented frontend to a same-origin API; it is not a Supabase client and talks to no third-party backend. Server allowlists/roles enforce access. Owner live changes use authenticated EventSource; a 30-second poll is a fallback. Riders refresh every 18 seconds/on focus.
6. First run creates a local one-time setup code file; it never creates a default password or prints a secret. One owner account is initialized through /setup/. Rider creation, reset and deactivation are owner-only. Passwords use salted scrypt, session cookies are HttpOnly/SameSite with server-side token hashes, and real HTTPS deployments enable Secure cookies through PUBLIC_ORIGIN. Setup cannot be reused after an account exists.
7. Defaults: Fresh Fold branding, ₱190/load service, 8kg/load, Asia/Manila, one delivery day, 15:00 cutoff, 40 loads/day. No shops/customers/riders are seeded, service areas start empty, and public bookings are closed until configured. All business rules are editable. Shop cost entry suggests ₱125 but the server never assumes this as a real cost.
8. Bags retain permanent customer codes; codes expand beyond four digits. Per-order tags, drop-off points and customer batch discounts do not exist. Loads and bags are distinct. Owner-only cost snapshots and generated totals persist through settings changes. Owner edits to an unchanged service/shop preserve original snapshots.
9. Rider APIs return fixed operational fields only. Alternate delivery stops omit pickup coordinates/landmarks. Shared rider routes are retained; per-rider assignment remains optional/unimplemented. All 64 status combinations are tested. Undo handles pickup, shop drop-off and delivery only for the same actor's last action within 60 seconds. UUIDs make tap/report retries idempotent. No separate client status is persisted.
10. New bookings use an IP-bound, one-use ten-minute arithmetic challenge, a honeypot check, phone/IP limits and pending approval. This removes the external Turnstile account but is weaker against sophisticated bots; internet deployments should add suitable trusted edge protections. The server uses socket IPs, never untrusted forwarded headers. All callers behind a proxy may share a bucket; trusted proxy-level limits can improve that.
11. Booking transactions protect capacity, duplicate returning orders, phone uniqueness, snapshots and receipt deduplication. New same-phone requests do not overwrite saved contacts/addresses; their submitted details and consent are recorded for owner review. Blocked personal links fail generically; same-phone new submissions still require owner review. Manual owner bookings may exceed public capacity or create multiple active orders intentionally.
12. Reports use delivered dates in the business timezone and rider pay dates. Money aggregates sum integer cents server-side before rendering; no binary-float accumulation is used for financial totals. Groups show contribution before unallocated rider pay; net margin subtracts pay once. Missing partner costs are flagged. Break-even excludes untracked overhead. CSV exports escape formula prefixes.
13. Backups use node:sqlite backup, including while the app is running, via the owner download or CLI. A persistent data directory/named Docker volume is required. Accounts/settings/events/order history live in the same SQLite database. Session/challenge/rate tables are internal, not exposed by generic table endpoints. Backup files are private and not committed.
14. Existing PWA/branding/design/labels/English-Filipino UI are kept. No API/customer data enters Cache Storage. Offline queues remain per account and retain failed taps. Offline authentication and an offline task-history cache are not provided. Undo toasts show the latest action and leave mobile screen space; this was corrected after real browser testing exposed overlapping toasts.
15. Production can run with one command or supplied start scripts; Docker/Compose are optional. Docker binds loopback by default and persists data in a named volume. No hosting, domain, router changes or public deployment were performed. HTTPS/LAN/device/physical-printer and native language/privacy review remain operator checks.
16. Tests now use an actual temporary SQLite HTTP server and real browser accounts, not mocked Supabase/Auth/Turnstile responses. Tests never populate the real local business database. Existing isolated checkouts are reused; do not create Git worktrees unless explicitly requested.
17. Out of scope remains online payments, automatic SMS/Messenger sends, background push, native apps, per-stop rider assignment, duplicate customer merging and QR bag labels. The optional track endpoint is retained. There is no email password-recovery service; trusted offline account recovery requires a server administrator.

18. Monterey compatibility: official Node 24 binaries require macOS 13.5+, but the Node 22 x64 support floor is macOS 11. The app supports Node 22.16+ (minimum for sqlite.backup); Node 22.23.3 was used for full API and browser tests on Linux. This establishes Node API compatibility, not a physical Mac test. CI runs Node 22 and 24. macOS Monterey instructions recommend the official Node 22 Mac installer.
