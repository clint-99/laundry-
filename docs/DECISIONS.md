# Implementation decisions

1. This replaces the initial Node/SQLite prototype with the requested static GitHub Pages + Supabase architecture. The prototype was copied to `/workspace/laundry-previous-version` before replacement; that local backup is not part of this repository or deployment. Its SQLite records are not imported. No production credentials or existing customer data were supplied.
2. Plain HTML, CSS and browser ES modules; no framework and no production build. Node/npm are only for a local static server, tests, and reproducibly bundling the pinned Supabase browser client. Only public site files are uploaded by Pages Actions.
3. `{{BUSINESS_NAME}}`, `{{HOTLINE}}`, and `{{FACEBOOK_PAGE_URL}}` remain business-setting placeholders. The landing/staff fallback wordmark is Fresh Fold. The booking page reads the live business name and contact details from public-config. REPOSITORY_URL points to the source setup guide (update it when forking). Set BRAND_NAME once in config.js for the static landing wordmark; logo is a second config setting, accent is --primary in ui.css.
4. Defaults: PHP symbol ₱, Asia/Manila, 8 kg/load, one delivery day, 15:00 cutoff, 40 loads/day, Morning/Afternoon/Evening. Timezone and business rules are editable. Optional seed contains a ₱190 service, ₱125 partner, two clearly labelled sample areas and one demo customer. No seed is automatically run.
5. Every active rider sees the shared operational route. Per-stop rider assignment is optional in the brief and not implemented. Ready orders are the delivery queue; no duplicate delivery-planning status exists. Today calls these “ready for rider delivery.”
6. Owner order overrides require a reason; direct status updates are blocked by a trigger. Orders and events cannot be deleted by application roles. Services/shops are archived by setting inactive, retaining historical references. Price and shop-cost snapshots can’t be forged or retroactively changed; changing service/shop takes a fresh snapshot. Editing loads changes the generated total. An unchanged service keeps its prior per-load price.
7. The reference SQL did not cover undoing shop drop-off. This implementation uses rider_actions and rider_undo for every rider tap, including drop-off. Undo is restricted to the same actor, last status event and 60 seconds from server acceptance. UUID action IDs make retries idempotent; reports also deduplicate by UUID. Status is always read back from the server; a queued card only says Waiting to sync.
8. Public bookings run in a transaction holding the settings-row lock, protecting public capacity and duplicate-active checks. New-customer same-phone requests never overwrite known details or expose whether the phone exists; submitted details and a review flag are in the owner's audit history. Blocked same-phone requests stay pending for owner review. Owner manual orders intentionally may exceed public capacity or create multiple active orders.
9. The browser supplies a request UUID for booking idempotency. Repeating identical requests returns the same receipt; changed payloads with the same ID are refused. A changed form after an uncertain save requires reloading/checking with the business. A fresh page creates a new request ID. Rate limits still count retries, deliberately limiting abuse.
10. Bag codes are permanent customer identifiers; no order tags or physical drop-off points. Code formatting expands beyond 9,999 without truncation. Tokens use two built-in cryptographic UUIDs (48 hex characters, approximately 180 random bits), avoiding assumptions about pgcrypto’s installation schema. Resetting a token invalidates the old link immediately.
11. Alternate delivery addresses do not return pickup landmarks or coordinates to riders during delivery. New and existing addresses remain owner-reviewable. Optional location is never required.
12. Reports are computed server-side in owner_report and protected by active-owner checks. Delivered dates determine revenue/shop costs; pay dates determine rider costs. Days/weeks (Monday start)/months use the configured timezone. Group contributions exclude unallocated rider pay; overall margin subtracts it once. Missing shop costs are flagged as provisional. Break-even is average rider pay/day divided by realized per-load contribution, excluding other overhead. CSV exports escape spreadsheet formula prefixes. Form price previews are labelled estimates; the database sets actual money.
13. Rider offline taps live in a queue keyed to the signed-in user in localStorage, not the service-worker cache. Queued IDs, target status and problem text remain on that device until synced/resolved. They never silently disappear on an error; conflicts require visible retry or explicit removal. If localStorage fails, keep the page open; the warning cannot promise crash durability. Undo must reach the database in its server-side window.
14. Service worker caches a fixed shell allowlist only. No APIs, sessions, task lists, addresses, or booking fragments enter Cache Storage. Offline shell does not imply offline authentication or a persisted task list. API responses use no-store. PWA service processes must restart on a new environment.
15. Staff-admin JWT verification at the gateway is disabled consistently with the other functions, but the handler independently calls Auth getUser and checks an active owner profile on every request. It can create/deactivate/reset only riders, not owners. A second owner is created through the documented dashboard + SQL process.
16. Rate-limit keys are salted SHA-256 hashes. The deployment must preserve a trusted client-IP header at the Supabase gateway; if absent, requests share an “unknown” bucket. Forwarded-header trust and real-IP enforcement must be verified after deployment, particularly if a custom proxy is introduced. CORS is not authentication; bearer tokens and Turnstile provide the relevant controls.
17. English is default. Booking copy has a Filipino toggle; translations require native review. Owner and rider interfaces are English. The privacy notice needs local legal review. Fonts use Google Fonts as requested, with system fallbacks; Supabase JavaScript is vendored locally at 2.118.0, not loaded from a CDN. Turnstile is the one required remote executable script, served by Cloudflare.
18. Customer merge, QR labels, rider-per-stop assignment, public tracking UI, automatic notifications to customers, online payments and native apps are not implemented. The optional track edge endpoint is supplied. Rider-pay entry is supplied in Reports. Browser notifications/sound are opt-in for a foreground owner workspace; no push notifications or background service are implied.
19. Tests use a real temporary PostgreSQL 18.4 binary on Linux with minimal Supabase Auth roles/functions and publication stubs. This checks actual SQL/RLS, not the hosted Auth/PostgREST/Realtime stack. Browser tests mock network APIs and Turnstile. Live account tests and hosting are distinct, pending owner account setup.
20. All setup uses the existing isolated checkout. Do not create worktrees unless explicitly requested. Do not commit credentials, local exports or the previous prototype archive.
